## Phase 6 failure (consolidated run 1): evidence and cause
* **What failed.** `p6-e2e` stopped at `planning_e2e.py` line 218 with `PermissionError: [WinError 5] Access is denied` raised by `subprocess.run(["docker", "exec", ...])` (a Windows process-launch error, not an assertion; 0 of its checks had failed). `p6-browser` then failed two steps of `e2e/planning-ui.mjs`: "the grid now shows the actual ... with its source - source not shown" and "after a reload ... - actual lost" (logs in `20261016-135413/p6-e2e.log`, `p6-browser.log`).
* **Cause of the browser failure: proven, reproduced.** Before the crash `planning_e2e.py` had created and approved a correction (`delta_units = -2`, note "two tills entered the same sale") on the same SKU, store and week the browser journey imports. Its only removal is the `cleanup()` at the end of the script, which never ran. The setup/cleanup of the browser world (`planning_data.py`) deleted only corrections whose note starts with `E2E`, so the correction survived. The grid then rendered the authoritative actual 11 with the correction (displayed actual 9, caption "11 -2 corr." in place of the source). The test's `getByText(/^11/)` matched that caption, so the wait passed, but the cell text began with "9" and had no "Imported" (hence "source not shown" and, after reload, "actual lost"). The application stored and returned the data correctly; the behaviour is by design (`Workspace.tsx` shows the correction beside the recorded actual).
* **Reproduction (2026-10-16).** Running `planning_e2e.py` with its final cleanup skipped left one APPROVED correction of -2; `planning_data.py` + `planning-ui.mjs` then failed with the identical two messages. After adding one `DELETE` of that correction to `planning_data.py` `cleanup()`, the same sequence passed ("all steps passed"), and the full `--only p6-` regression passed (run `20261016-164235`).
* **Fix applied.** `e2e/ai/planning_data.py` `cleanup()` now also removes the `planning_e2e.py` correction. No product code changed.
* **Not explained: the `docker exec` PermissionError.** The original trigger of the crash is an environment failure on one `docker.exe` launch; it has not recurred in three later runs and its cause was not found (candidates: antivirus or a transient handle/permission problem on Windows, or concurrent tool activity). It is left **open**. Follow-up: if it recurs, capture the process owner and Windows event log; optionally make `stack.sql` retry a failed launch once.
* **Residual fragility.** `planning-ui.mjs` identifies the actual by `getByText(/^11/)`, which can match the caption; a stricter assertion on the cell's first text node would have named the real cause immediately. Not changed (test change beyond the confirmed defect).
