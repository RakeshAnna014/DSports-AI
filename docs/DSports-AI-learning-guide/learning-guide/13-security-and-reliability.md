# 13. Security, reliability and failure handling

Principle used throughout: **a security property counts only where code enforces it** (a registry check, a SQL filter, a Java ownership check, a signature), not because a prompt asks the model to behave. Each control below names the enforcing code.

## 1. Authentication versus authorization

| Concern | Where | Notes |
|---|---|---|
| Authentication (who are you?) | Java: `JwtWebFilter` + `JwtTokenProvider.validate` (`backend/bootstrap/.../JwtWebFilter.java:36-61`); Python: `verify_token` (`ai-service/app/auth/jwt.py:45-72`) | same HS256-family shared secret; Python rejects `alg=none` and asymmetric algorithms (`jwt.py:22-25, 47-52`), requires `exp` and a UUID `sub`; Java requires >= 32-byte secret (`JwtTokenProvider.java:27`) |
| Authorization of commerce data | **Java only** (use cases, `SecurityConfig` roles) | the AI service forwards the caller's own token, so it can never see more than the customer can |
| Authorization of AI features | Python registry (`required_role`, `requires_auth`), REST `admin` dependency, input guard | defence in depth, never the only layer |
| Identity of the caller in AI code | `Principal` from the verified token; `customer_hash` for logs/state | request bodies never supply identity (`test_identity_cannot_be_supplied_by_the_request`) |

JWT propagation: browser -> (Vite proxy) -> AI service (verifies) -> Java (verifies again with its own filter) with the **same bearer token** and an `X-Correlation-Id` (`DSportsClient.request`, `dsports_client.py:32-47`).

## 3. Reliability and failure handling

* **LLM timeout / quota / outage:** `VertexGemini` maps errors to `LLM_*` codes; `ResilientLLM` retries once on timeout/error (not on quota), opens the circuit breaker after 3 consecutive failures for 30 s and fails fast with `AI_UNAVAILABLE` (`resilient.py:24-95`). Consequences by caller: Tier 1 -> rules fallback or an "unavailable" message; explanations -> deterministic text + disclaimer; embeddings -> keyword-only retrieval; inventory `_compose` -> deterministic headline. **Quota exhaustion looks like quality loss**: classification can return `OUT_OF_SCOPE`. During Phase 3 validation this invalidated several evaluation runs; those results were classified as environmental (doc 14, doc 15).
* **Downstream business API failures:** `DSportsClient` maps timeouts/connection errors/5xx/4xx to `ToolError` codes (`UPSTREAM_TIMEOUT`, `UPSTREAM_UNAVAILABLE`, `UPSTREAM_ERROR`, `FORBIDDEN`, `NOT_FOUND`, ...) without echoing upstream bodies (`dsports_client.py:41-83`). Nodes say "I couldn't get ..."; the support flow reports "could not check ..." and **creates nothing** (`UNVERIFIABLE`).
* **Database failures:** the AI service starts without the AI database and serves from memory for conversations; durable operations (pending actions, audit) refuse rather than degrade silently (`state.py:193-220`). Java relies on R2DBC pooling and transactions; domain errors map to HTTP codes.
* **Partial failure:** parallel investigation tool calls fail independently; the investigation records which lookups failed (`inv.unverified`) and `decide` only treats critical lookups as blocking.
* **Retry behaviour:** LLM calls retry once; tool calls do not retry (reads are cheap to re-ask; writes must not be repeated); WRITE retries are made safe by idempotency keys.
* **Graceful degradation when AI is unavailable:** the storefront, orders, checkout and the support-case pages (Java) work without the AI service; the assistant UI shows an unavailable state (`aiStore.fail`). Verified by `shop-with-ai-down` and the support browser step "the AI service down".
* **Audit and traceability:** AI `audit` rows for every proposal/confirmation/execution; Java `support_case_events`; `inv_audit` for inventory; correlation id in every log line and error body; usage rows per model call.
* **Sensitive information in logs:** JSON formatter with redaction of sensitive keys and value patterns (JWTs, bearer headers, e-mails, DB URLs, private keys, UUIDs) (`obs/logging.py:15-49`); uvicorn access log disabled to avoid raw query strings (line 95); the middleware logs only the path (`middleware.py:32-37`); customers appear as an HMAC hash. Tests: `test_secrets_never_reach_the_log_output`, `test_authenticated_request_logs_hash_not_raw_customer_id`. Caveat: free-text customer messages are not logged by the service but are stored in `conversations.state`/case rows in plain text (needed for the product; subject to retention policy that does not yet exist).
* **Hallucination controls:** see T11; plus no tool calling by the model, facts only from tools.

## 4. Known security gaps (all documented, none hidden)
1. Pattern-based input guard and sanitiser: first-run held-out evaluations of Phase 1, 2 and 3 each found missed phrasings (patched with regression tests); the guard is the weakest layer, which is why tools, registry, SQL and Java enforce independently.
2. JWT shared HS256 secret and browser `localStorage` tokens (inherited from Phase 1). `application-local.yml` has a development-only fallback secret (`SYNTHETIC / POC` environment; `application.yml` itself requires `JWT_SECRET`).
3. No retention/cleanup of AI conversations, audit and usage rows.
4. In-process rate limiting (single instance).
5. Payments are a mock gateway; no real money flows.
6. No load, penetration or dependency-vulnerability testing was performed (`UNKNOWN`/not run).
7. No service-to-service authentication besides the forwarded customer token (the AI service cannot act as a system actor).
