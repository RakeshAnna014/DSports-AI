# ADR-019: Cricket players, teams, matches and ball-by-ball scoring

Status: accepted; steps 2a (players and teams, V53), 2b (match setup, V54), 2c (scoring rules engine) and 2d (ball-by-ball API and scorer screen, V55; V56 adds the TRUNCATE guard) and 2e (public scorecard and live list, no migration) implemented, 2f planned. Plan: `docs/plans/cricket-features.md`. Builds on ADR-017 and ADR-018.

## Context

Phase 2 of the cricket plan: players (guests allowed), teams, match setup, scoring and a public scorecard. Where the plan file differed from the code is recorded in "Differences from the plan" below.

## Decisions (whole phase)

* **One module, `backend/cricket`** (`com.dsports.cricket`, layered like `ground` and `support`), not three: players, teams, matches and scoring reference each other too closely to be separate modules. The scoring rules engine will live in `domain.rules`, pure Java with no framework imports (enforced by a test).
* **Event log, state folded from events** (2d): an append-only `ball_events` table, a stored snapshot written in the same transaction, unique `(match_id, seq)` and `(match_id, client_event_id)`, a per-match advisory lock, `expectedSeq` conflicts as `409 SCORE_CONFLICT`. The server derives striker, bowler and over/ball; a client sends only the outcome.
* **No new role.** Ownership is checked in the use cases (creator, captain's account, assigned scorer), as in the ground module.
* **Scorecards are public by link, names only** (2e, built). Phone numbers, emails and every id but the match's own are never in a public response.

## Step 2a: players and teams (V53)

* **A player exists without an account** (a guest, created by someone who vouches for them) and may be linked to a registered customer. A customer is linked to at most one player (unique index).
* **A phone number is a search hint, never proof.** `customers.phone` is unverified and there is no OTP, so linking by phone alone would let anyone take over another person's profile. Instead a **claim** is requested by the registered customer and **approved by the person who created the guest** (or an administrator); approving rejects the other pending claims on that guest, in one transaction. The phone search (`GET /players/claimable`) returns only a shortened name ("Arjun K.") and at most 5 results, so it cannot be used to look up names from numbers.
* **Phones are unique per creator, not globally** (`(created_by, phone)`): two captains can each add the same real person. This replaces the plan's "unique phone per player". Phone numbers are normalised (`+91` assumed for 10 digits) and only ever shown to whoever created the profile.
* **Two profiles cannot be merged yet**: a customer who already has a linked player cannot claim a guest (merging would mean rewriting match history once matches exist).
* **Visibility returns 404, not 403**, for strangers (players, teams, claims), so ids cannot be probed. A member whose account is linked can see a team but not change it (403); the creator and the captain's own account can change it.
* **Teams:** unique name per creator (any case), at most 30 players, at most one captain (a partial unique index in the database as well as in the domain), the captain cannot be removed before another is chosen, an archived team is frozen, every change is version-checked through the team row.
* A claimant's name and email are shown only to the person who must decide the claim, through a port (`CustomerDirectoryPort`) implemented in bootstrap; the cricket module does not depend on identity.

## Step 2b: match setup (V54)

* **A match** has two different teams, overs (1 to 100), a ball type (LEATHER or TENNIS) and rules stored as columns (balls per over, players per side, bowler overs limit, wide and no-ball penalties, free hit, last man stands), all defaulting to the standard values and validated against the match length. Umpires are an optional text, not a table.
* **Lifecycle:** this step covers `SCHEDULED` and `TOSS_DONE`. The CHECK already lists the whole lifecycle so it never has to be widened. `start` arrives in 2d with the first scoring event, because the openers only exist once scoring does. Setup (settings, toss, XIs) is locked once the match leaves those two states.
* **Who can do what:** the creator changes settings and scorers; the creator or an assigned scorer records the toss (correctable until the start) and the playing XIs; people with a team in the match (as creator, or through a linked player) can only look. Everyone else gets 404. Scorers are found by registered email (`404 USER_NOT_REGISTERED` otherwise); there are no invite links.
* **Teams:** a creator can only pick teams they can see (created by them, or with a linked player of theirs), so a match against someone else's team needs that team to be visible to the creator for now; invitations are a later feature. An archived team cannot play a new match.
* **Playing XI:** between 2 and the players per side, in batting order, all members of that team, nobody twice, nobody on both sides (primary key and unique batting order in the database too). Scorers who are not on a team get each side's squad in the match view (`squad`, scorers only) so they can pick from it.
* **Venue booking (optional):** must be the creator's own, `CONFIRMED`, for cricket, and not already hosting another match (unique index). The venue name and city are copied onto the match, and the start time too when none was given. The cricket module reads the booking through `BookingLookupPort` (implemented in bootstrap over the ground module's tables); it has no foreign key to it.

## Step 2c: the scoring rules engine

* **Pure functions in `domain.rules`.** `ScoringEngine.apply(state, command)` returns `Accepted(newState)` or `Rejected(violation, message)`; a rejection changes nothing. No framework, clock or randomness (a test reads the package's imports and source). The full design, the dismissal table and a hand-scored innings are in `docs/plans/cricket-2c-scoring-engine.md`; that innings is a golden test.
* **The client sends outcomes only.** Striker, non-striker, bowler and over are derived. The next batter or bowler is a separate command, required when the state says it is needed, and a ball is refused until it is given.
* **Replayable.** The state is a fold of accepted commands (`replay`), which is what the 2d event log will rely on; property tests check this with thousands of random commands.
* **Dismissals** follow the approved table (no separate "handled the ball"), with the free hit restricting it further. A run out names the batter and the end, which decides who is left where and so who faces next.
* **Strike:** one swap per run actually run, none for a boundary, and one at the end of an over. A lone last-man-stands batter never swaps.
* **Bowlers:** none twice in a row, and a limit of credited overs: unless set for the match, the larger of a fifth of the match and the match shared between the bowlers a side can field (players per side minus one), each rounded up, so an 11-a-side 20-over match allows 4 and a 4-a-side one allows 7. An over with a mid-over change counts for the bowler with most legal balls (a tie goes to whoever started it). The injured bowler may bowl again later; only the one who finished the over cannot bowl the next. If nobody is under the limit, the limit is waived as a last resort so the innings can finish (and, if only one bowler is left who bowled the previous over, that rule too); each waiver is returned on the command's outcome so it is stored on its event, kept in the innings state and listed on the scorecard.
* **Bat runs are at most 7 per ball; the wide and no-ball penalties are added on top.**
* **Retired hurt** is not a wicket and the batter may come back; **retired out** is a wicket and he cannot. Both are accepted between balls only.
* **Result** is computed from the two innings every time and never stored on its own, so an undo re-derives it. A revised target is the scorer's number (no DLS calculation).

## Step 2d: ball-by-ball scoring (V55)

* **The log is the truth.** `ball_events` is append-only (a trigger refuses UPDATE and DELETE): one row per accepted command, with a unique `(match_id, seq)` and a unique `(match_id, client_event_id)`. `match_snapshots` is the read model, written in the same transaction. Every request rebuilds the state by folding the effective log with the 2c engine; a test checks that the snapshot equals that fold after every step.
* **Two scorers cannot corrupt a match.** One transaction per request holds a per-match advisory lock. Inside it: a retry of a command already in the log is answered as done (idempotency comes first, so a lost response is never a false conflict); a request made from an old view (`expectedSeq` is not the latest) is `409 SCORE_CONFLICT` carrying the current score and what happened since; a match whose window has closed is `409 MATCH_LOCKED`; then the engine decides, and a refusal is `422 SCORING_REJECTED` with the rule's code. The two unique keys are the second line of defence if the lock were ever bypassed.
* **Undo is an event.** An `UNDO` voids earlier commands (it deletes nothing); the state is the fold of what is left, so overs, wickets, the free hit, the over credit and the result need no special case. `BALL` mode takes off the last ball and what was chosen after it (the new batter, the new bowler); `COMMAND` mode takes off one command. It never crosses the start of an innings, and the screen asks first when it would reopen an innings or a finished match. There is no redo.
* **The correction window is anchored to the first finish.** For 24 hours after the match first finishes (completed, abandoned or no result) commands and undo are allowed. Undoing and finishing again does **not** restart the clock (`first_finished_at` is never cleared). Only an administrator's unlock, with a reason, grants a fresh 24 hours from the unlock; it is an `ADMIN_UNLOCK` event in the log (who, when, why). A correction left half-done at the deadline is locked as it is, and an administrator can reopen it.
* **An optional fielder** (from the fielding XI) can be named for caught, stumped and run out, and a scorecard reads "c Ravi b Tarun", "st Ravi b Tarun", "run out (Ravi)". Shot positions are not recorded.
* **Waivers are on the record.** When every bowler left is at the over limit, the limit is set aside as a last resort; the waiver is stored on the event, kept in the innings state and listed on the scorecard.
* **The client holds no cricket rules.** The server's view says what is needed next, which dismissals the next ball allows and who may bat or bowl. A change goes through a durable one-slot outbox on the phone (saved with its client event id, retried, cleared only when the server answers), so a ball is neither lost nor counted twice. Many balls offline would need a copy of the engine on the phone, which is step 2f. The run-out end defaults from the runs completed (striker out: bowler's end after an even number of runs, striker's end after an odd number; the non-striker the other way) and the scorer can change it.
* **What the log protects against, and what it does not.** Three guards: a row-level trigger refuses UPDATE and DELETE on `ball_events` (V55); a statement-level trigger refuses TRUNCATE, including `TRUNCATE ... CASCADE` from `matches` (V56; the migration guard test allows the word TRUNCATE only in that exact trigger definition); and the two foreign keys into `matches` have no cascade, so deleting a match (or a team a match uses) that has a log is refused by the database. No application code deletes matches, teams or players. A database superuser can still disable triggers or drop the table; that is outside what the application can prevent and is a matter of database permissions.
* **The snapshot can be rebuilt from the log, including the lock dates.** `first_finished_at` is the time of the first log entry after which the match was finished (the entry's own time, which is also what the use case stamps, so the two always agree); `unlocked_until` is the last `ADMIN_UNLOCK` entry's time plus 24 hours. `ScoringLog.windowOf` derives both. When the snapshot row is missing every request derives the window from the log instead of treating the match as open, so a lost snapshot can never reopen a locked match; `ScoringUseCase.rebuildSnapshot` writes the derived snapshot back. Tests delete the snapshot after a scored match, an undo, a re-completion at hour 23 and an admin unlock, and check the lock state is identical before and after, and that the rebuilt snapshot equals the original.
* **Locked messages.** A refused change says "finished more than 24 hours ago" when the match had finished, and "The correction window closed while the match was in progress" when a correction was left half-done. The scorer screen warns in the last hour ("This match locks in 38 min. Finish your correction or ask an administrator to unlock it."), and the "You can correct this match for ..." line ticks down by itself. When the clock passes the deadline the screen asks the server again; the server stays the only judge of the lock.
* **One scorer tab per match per browser.** The unsent ball is one saved slot per match, shared by every tab of a browser. A tab takes a lease (a record in local storage refreshed every 2 seconds and watched through the `storage` event, so it works over plain HTTP, where the Web Locks API does not exist). A second tab of the same match is read-only, says so, shows the score refreshed every 5 seconds, never sends or discards the saved ball, and takes over automatically (and then sends the saved ball once) when the first tab closes or goes quiet for 10 seconds. A tab frozen in the background (phone browsers throttle or freeze them, so its timers and storage events may not have run) looks at the lease again the moment it is visible or focused, and again immediately before anything is saved or sent, so it can never send a ball after another tab has taken over. It only covers tabs in one browser; a second scorer on another device is the server's conflict sheet. With browser storage blocked the page cannot tell tabs apart and simply scores.
* **Routes:** `GET /api/v1/matches/{id}/scoring`, `POST .../scoring/commands`, `POST .../scoring/undo`, and `POST /api/v1/admin/matches/{id}/scoring/unlock` (ADMIN). Errors carry an optional `details` object (a new field of the shared error body).

## Step 2e: the public scorecard and the live list (no migration)

* **Two public routes, and only two.** `GET /api/v1/matches/{id}/scorecard` and `GET /api/v1/public/matches/live?city=&page=&size=` are `permitAll` and read-only. Everything else under `/api/v1/matches` (setup, scoring, "my matches", unlock) stays behind a sign-in. **The live list has a path of its own and the security rule looks at the path only.** The first version of 2e shared `/api/v1/matches` with "my matches" and told them apart by a `status` query parameter, in the security rule and in the controller; that made the one rule that decides who is signed in depend on how a query string is spelled (`status=live`, `%4CIVE`, repeated or comma-separated values), so it was dropped. `GET /api/v1/matches` is now only ever "my matches" and answers 401 without a token whatever follows the `?` (a `status` parameter is ignored). `SecurityPolicyTest` pins both public routes anonymous, `/api/v1/matches` with ten spellings of a `status` parameter as 401, `/matches/x`, `/matches/x/y/scorecard`, `/matches/x/scorecards`, `/public/matches`, `/public/matches/live/x` and `/public/matches/livex` as 401, and every non-GET method on both public routes as 401.
* **A match is public once its first innings has started** (`MatchScore.hasStarted()`): before that, and for a match abandoned before a ball, the scorecard is 404, the same answer as a match that does not exist, so ids cannot be probed. Every started match is readable by anyone who has the link and appears in the live list while it is being played; the creator has no "private" switch yet. That is a product rule from the brief, and the first thing to change if it is not wanted.
* **Names and numbers only.** `PublicScorecard` is its own type, built from the stored snapshot and not from the scorer's view: no ids except the match's own (which is in the link), no emails or phones, no booking, claim, scorer, user or version data, no correction window and no undo state. A test serialises a whole finished scorecard and a list page and checks the only UUID in them is the match's. It reuses the scorer's innings view for batters, bowlers and dismissals (so "c Ravi b Tarun" and the bowling figures can never disagree between the two screens) and then drops the ids. The run rate and the required rate are computed on the server, once, to two places; they are null when no ball has been bowled or none is left.
* **ETag = the last event's seq plus a digest of the whole response** (`"36-9f2c1d04a7be3c55"`). The seq alone was the first design, but a player or team can be renamed (or the match's details changed) without a ball being scored, and then the page would have kept the old name until the next ball. The digest is the first 8 bytes of a SHA-256 over the response record's `toString` (every component in order, so a field added later is covered with no change), computed by `PublicScorecardEtag`; the seq in front keeps it readable. An undo is an event, so it changes the tag; so does a rename, with the same seq. **Trade-off:** the tag now needs the whole scorecard built, so a poll that finds nothing new costs the snapshot read plus the name lookups (a handful of small indexed queries) instead of one snapshot read, and still sends no body (304). That is cheap at one request per viewer every 4 seconds; if it ever is not, cache the built card per `(match, seq, names version)` rather than going back to the seq alone. A lost snapshot does not hide a match or change its tag: it is derived from the log, as in 2d. `Cache-Control: no-cache` makes a client ask every time and rely on the tag.
* **The live list** is `IN_PROGRESS` and `INNINGS_BREAK` matches, most recently scored first, an optional city compared case-insensitively (the `ix_matches_status_city` index from V54 covers it), paginated with `hasNext` instead of a count query (page size 1 to 50, default 20). `status` must be `LIVE`; anything else, a negative page, a size above 50 or a city over 80 characters is a 400, never a 500. Each item carries the teams, overs, city, venue and the score of each innings so far.
* **The page** (`/m/:id`, inside the shop layout, mobile first) shows the score, overs, run rate, the target with the runs and balls needed and the required rate, the result, and each innings (newest open) with batters and how they were out, extras, yet to bat, bowlers, fall of wickets and bowling waivers. It polls every 4 seconds with the ETag, **pauses while the tab is hidden** and asks at once when it is visible again or the network returns, backs off (8, 16, 30 seconds) while the server fails and keeps the last score on screen with a notice, and **stops when the match is over** (with a "check again" button, because an undo within 24 hours can reopen a finished match). A match that has not started says so and is checked again every 10 seconds, so a link shared early lights up at the first ball. It uses its own HTTP client with no stored token: a signed-out visitor never triggers the shared client's refresh-or-go-to-login behaviour, and a signed-in user's token is not sent with a public read.
* **Sharing.** "Copy link" and "Share on WhatsApp" are on the scorer screen (once an innings has started), the match setup page (once the match has started) and the public page. A phone on the local network opens the app over plain http, where `navigator.clipboard` does not exist, so copying falls back to the older copy command and then to showing the link to copy by hand. WhatsApp is a plain `https://wa.me/?text=` link opened in a new tab with `noopener`. The link uses the address the page was opened from, so it is only as public as that address is.
* **The live list page** (`/live`, "Live cricket" in the header) refreshes every 15 seconds, filters by city after a short typing pause and loads more pages on request.
* **Tests.** Use case (14: not started and abandoned-before-start are 404, names and dismissals, the chase and required rate, the result, an undo and a rename move the ETag, a lost snapshot changes nothing, no ids, list filtering, ordering, paging and validation), repository (1, real PostgreSQL), HTTP over real authentication (7: anonymous read, ETag and 304, a rename changing the ETag and the next poll getting 200 with the new name, a finished match, the list with city and paging, `/matches` always being "my matches", bad parameters), `SecurityPolicyTest` (public-route rows, ten `status` spellings that stay 401, and the method checks), frontend (polling hook 9, page 8, list 5, sharing 6, plus the scorer and setup buttons), and `e2e/cricket-ui.mjs` (an **emulated** run: a phone-sized Chrome scorer and a signed-out desktop Chrome following it; it is not a real phone).

## Step 2f-3: what the server gives a phone that scores offline (V57)

* **`GET /api/v1/matches/{id}/scoring/engine-state`:** the setup, the whole log (commands as the request bodies, undos with what they voided, unlocks), `engineVersion`, `stateFingerprint` and `ready`. Same access as the scoring view; ids only. The fingerprint is computed in main code (`StateFingerprint`, reflection over the domain records, canonical text hashed with SHA-256) and equals the one recorded in the shared vectors for every step of every vector file (`StateFingerprintTest`); the TypeScript engine reproduces it. Sample answers are written by the Java build and read by the TypeScript parser, so the route's JSON shape is proved from both sides.
* **`ScoringView`** gains `engineVersion` and `stateFingerprint`; **events** gain `mine`, `clientEventId` (the asker's own events only) and `tappedAt`.
* **`tappedAt`** (V57, nullable column, optional request field) is display only: not in the request fingerprint, never read by a rule, the 24-hour window or the ordering (the seq and the server's `created_at` decide those), clamped to the server's receipt time in code and by a CHECK in the database. The migration is a plain `ADD COLUMN`: tests prove an insert with and without it, that UPDATE, DELETE and TRUNCATE are still refused, and that a database that already holds V56 events upgrades with them untouched.
* **Alternatives:** a separate fingerprint route (rejected: it would race the log); the fingerprint over the codec's JSON (rejected: the application layer would depend on infrastructure, and a reflective writer cannot drift from the records); a batch route (not needed: one-by-one is idempotent and tested with 60 and with two tabs at once).

## Differences from the plan

| Plan | Code |
|---|---|
| migrations V49 to V53 | head was V52, so Phase 2 uses V53 onward |
| packages `.team`, `.match`, `.scoring` | one module `cricket` with layered packages |
| unique phone per player | unique per creator; claims need approval |
| PWA with an offline queue | no PWA support exists in the repo; a localStorage retry queue in 2d, installable PWA later |
| `match_officials`, shot x/y, `innings_snapshots` | umpires as optional names, no shot map, one snapshot row per match (2b/2d) |

## Consequences

* Claiming a profile needs the guest's creator to act; an unresponsive creator blocks it (an administrator can decide any claim).
* No penetration test or certification has been performed; the security tests are the project's own (`SecurityPolicyTest` classifies the routes; `CricketPlayersAndTeamsHttpIntegrationTest` covers visibility over real auth).
