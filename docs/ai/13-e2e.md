# 13 — End-to-end scenarios and regression

Everything here ran against the **real running stack**: the Java backend with PostgreSQL, the AI service, real Gemini on Vertex AI,
pgvector, and a Tika server with Tesseract OCR. No DSports API, model or vector store is mocked. The only deliberate failure injection
is scenario M, which starts a second AI instance whose Google credentials are made unusable.

Run on 2026-10-07.

## Scenarios A–M (`e2e/ai/ai_scenarios.py`) — 64 checks, 64 passed

Each scenario registers real customers, buys, pays and delivers real orders through the public APIs, talks to `/ai-api` as that
customer, and checks the response, the tools that ran, and the database.

Findings from running them against the real stack (all fixed, with tests): an HS256-only JWT check rejected the backend's HS384
tokens; Gemini thinking tokens truncated answers; the semantic ranking factor was relative and promoted weak matches; retrieval names
were being counted as evidence by the grounding check; and the input guard missed "I am the admin" and configuration-extraction phrasing.

## Browser journey (`e2e/ai-ui.mjs`, Playwright, real Chrome) — 13 steps, all passed

Guest: launcher opens the panel; product discovery shows verified cards and a separate AI explanation; knowledge answer shows citations;
account questions ask the guest to sign in and return no data.
Customer: normal login form; orders card (Tier 0); tracking card; return-eligibility card; "return them" opens the confirmation dialog and
no return exists until **Confirm**; Confirm creates exactly one return; reorder asks for confirmation and fills the real cart (header
badge updates); a prompt-injection message is refused in the UI; with the AI service unreachable the panel shows a clear message while the
rest of the shop keeps working.

The run fails on any page error, 5xx, or console error. The storefront's own `GET /api/v1/cart` and `GET /api/v1/wishlist` return 404 for
a brand-new customer; those two are expected and whitelisted by exact URL. The journey found and fixed an invalid DOM nesting (a chip
inside a paragraph) in the tracking card.

### What this regression found (all fixed or explained)

1. **Real backend defect: unstable catalogue paging.** `GET /api/catalog/products` sorted by `created_at` only; most products share one timestamp, so with 134 products
   spanning two pages PostgreSQL could order tied rows differently per request and the same product appeared twice while another was skipped (seen as a React duplicate-key error and
   a strict-mode selector violation). Fixed with `id` as the final sort key; unit-tested (`ProductOrderingTest`).
2. **Test fakes had an invalid UUID** (the gym-bag id had 13 digits). Unit tests never validate UUIDs; the integration tests did. Fixed.
3. **Stale expectations after the catalogue grew:** integration tests hard-coded 5 products (now derived from the fixture); the browser journeys expected the old heading "Recommended for you"
   (now "Personalized for you") and counted assistant messages across both the Home page and the drawer (now scoped to the drawer); evaluation cases S02 and S09 expected one specific first
   product for "football boots" / "basketball shoes", but the catalogue now holds several equally valid ones, so the expected first product (cheapest first) was updated and all valid candidates listed as relevant.
4. **A Phase 1 invariant was revised on purpose:** the AI database used to hold no price or stock columns. The Phase 2 mart stores a catalogue price snapshot and POC stock positions, so the
   test now checks the customer-AI tables are unchanged and the `inv_*` tables hold no customer, order or payment identifiers.
5. **A misleading "495 tests":** when Testcontainers cannot reach Docker the 29 container tests silently skip; with `DOCKER_HOST` and `-Dapi.version=1.44` set (see baseline docs) all 526 run.
6. **Environmental noise, not code:** one evaluation run failed 10 cases while Gemini's circuit breaker was open and the service process had stopped (the log was overwritten by the restart, so the exact cause is not recoverable);
   a clean re-run passed 83 / 83. A run that spanned the laptop sleeping overnight produced timeouts and was discarded.

The existing `ui-flow.mjs` capture scenarios need the backend started with the mock-payment flags shown above.

## Gaps and honest notes

- `create_support_case` is out of scope: there is no support-case backend and no fake tool was added.
- A scripted Playwright journey was run on desktop Chrome only; no mobile viewport or accessibility audit was done.
- The sample catalog and knowledge base are demo data; real-world retrieval quality is not measured.
- The held-out 26 / 26 is a post-fix regression, not a fresh held-out estimate ([09](09-evaluation.md#honest-limits)).
- Costs are estimates from an operator-supplied price table, not billing data.
- The repository has no CI pipeline; these runs are manual and are reproduced by the commands in [12-local-development.md](12-local-development.md).
