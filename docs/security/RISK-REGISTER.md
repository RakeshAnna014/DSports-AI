# Security risk register and remediation plan

Derived from [THREAT-MODEL.md](THREAT-MODEL.md) (R1 to R11) and the observed [AUTHORIZATION-MATRIX.md](AUTHORIZATION-MATRIX.md). Written 2026-10-16 as a planning document: **no remediation below is implemented unless stated**. Severities are the project's own judgement (impact if the risk materialises, tempered by how much an attacker must already have), not a CVSS score. This is not a penetration-test report and no penetration test has been performed.

## Priority order
1. R10 (a dev profile reaching a shared environment) - cheapest fix, highest blast radius.
2. R1 and R2 (token storage and shared signing secret) - the two ways one small compromise becomes full admin access.
3. R3 (role changes not taking effect) and R6 (no dependency scanning) - control gaps that hide other problems.
4. R4, R8, R9 (database privilege, retention, provider terms) - needed before real customer data.
5. R7, R11, R12, R5 - low severity.

## Register

| ID | Severity | Component | Exploit scenario | Existing mitigation | Proposed remediation | Verification test (existing or proposed) |
|---|---|---|---|---|---|---|
| R10 | **High** if misdeployed | Java `local` profile, AI `AI_ENV=local` | The service is started with the development profile or `AI_ENV=local` in a shared or internet-reachable environment: `/metrics` and API docs are open, and `application-local.yml` carries a documented dev-only secret, so an attacker who knows the repository can forge tokens | `prod` profile has no defaults and disables docs; AI protects `/metrics` and closes docs when `AI_ENV` is not `local`/`test`/`dev`; `JWT_SECRET` must be at least 32 bytes | Startup guard: refuse to start with the `local` profile or `AI_ENV=local` when the database host is not `localhost`/the compose service, or when `JWT_SECRET` equals the documented dev value. Document the production checklist | Proposed: unit test for the guard in each service; existing `test_ops_and_config.py` already proves the protected `/metrics` and closed docs |
| R1 | **High** (low likelihood) | Frontend token storage | Any cross-site-scripting bug lets a script read `accessToken` and `refreshToken` from `localStorage` and take over the account for up to 7 days | No `dangerouslySetInnerHTML`; stored links pass `safeHref`; model and external text rendered as text; 15-minute access tokens | ADR first, then HttpOnly `SameSite` cookie session with CSRF protection and a refresh-token rotation/revocation table in Java; strict Content-Security-Policy meanwhile | Existing: `safeUrl.test.ts`. Proposed: browser test that scripts cannot read tokens (`document.cookie`/storage empty), CSRF negative tests, CSP report-only check |
| R2 | **High** (low likelihood) | Shared HS256 secret, Java and AI service | Whoever reads the secret from the AI service's environment or memory can mint an ADMIN token accepted by Java | Secret only from environment; 32-byte minimum; `iss` and `aud` required on both sides; AI service forwards but never mints tokens | Asymmetric signing: Java signs with a private key and publishes a public key (JWKS); the AI service holds only the public key. Rotate the secret meanwhile and store it in a secret manager | Existing: `JwtTokenProviderTest`, `SecurityPolicyTest`, route sweep forged-token cases. Proposed: test that the AI service cannot produce a token Java accepts |
| R3 | Medium | Java identity roles in token | An administrator removes a user's role (or disables the account) but the old token keeps working until it expires (15 minutes). Refresh does not extend this: `RefreshTokenUseCase` reloads the user, refuses deleted, disabled or locked accounts, rotates the refresh token and revokes all of a user's tokens if a revoked one is replayed | Short access-token life; refresh rotation and reuse detection; account status re-checked at refresh | Per-request role/status lookup for sensitive routes or a token-revocation list keyed by `jti`/user version, so a removed role or disabled account takes effect immediately | Proposed: integration test "removed role / disabled account loses access on the next request" (today it holds until the access token expires, at most 15 minutes) |
| R6 | Medium | Java and Python dependency trees | A known-vulnerable library is shipped unnoticed | `pnpm audit --prod` is clean and is a validation step (`sec-fe-audit`) | See "Dependency scanning and CI" below | CI job result; failing build on high/critical |
| R4 | Medium | PostgreSQL accounts | A defect (for example a future injection) runs with the owner account that can alter or drop any table | Parameterised SQL, allow-listed sort fields, hostile-input sweeps (690 query and 360 body probes) | Separate roles: a migration owner (Flyway) and a runtime role with only DML on its own schema; the AI service role gets no access to `dsports`; test databases separate | Proposed: integration test connecting as the runtime role to prove DDL and cross-database access are denied |
| R8 | Medium | Conversations, usage, audit, logs | Personal data and free text accumulate without a limit; deletion and access requests cannot be met | Conversations expire by TTL (`AI_CONVERSATION_TTL_H`); logs and audit are redacted; customer hash instead of id | Decide retention per table with the business, add scheduled purge jobs and a customer-data export/deletion procedure | Proposed: test that purge removes rows older than the period and leaves audit integrity checks intact |
| R9 | Medium | Model provider (Gemini on Vertex) | Prompt text leaves the system; provider terms or region may not match obligations | Only fenced, minimised text is sent (first name only; no address, phone, e-mail, payment); minimisation tests | Legal review of the provider terms, region and retention; a switch to disable model wording per environment | Existing: `test_tools_and_prompt_injection.py` (7 customer messages) and the privacy assertions in `security_e2e.py` |
| R7 | Low to Medium | Rate limiters, call budgets, caches (in memory) | With more than one instance the limits multiply, weakening brute-force and cost controls | Limits exist and are tested per instance | Shared store (Redis is already on the roadmap) or gateway-level limits | Proposed: multi-instance test once a shared store exists |
| R11 | Low | Sourcing allow-list | An allow-listed domain's owner turns hostile and serves hostile pages | Content is untrusted data and sanitised; SSRF controls: allow-list, public addresses only, connection pinned to the validated address, per-hop redirect checks, size/type/time caps, robots.txt; images by magic bytes | Periodic allow-list review by the buyer admin; optional content-hash change alerts | Existing: `test_ssrf_and_hostile_sources.py` (64 cases) |
| R12 (new) | Low | AI planning role sets | `SUPER_ADMIN` (a Java `UserRole`, level 7) is accepted by the planning workflow's admin set, but Java's route rules check `ADMIN`, so the two services disagree about that role | Roles are granted only by SQL; no API grants `SUPER_ADMIN` | Decide whether `SUPER_ADMIN` exists operationally: either remove it from `planning/workflow.py` `ADMIN_ROLES` or make Java treat it as an administrator, then add it to the authorization matrix personas | Proposed: matrix persona and unit test asserting both services agree |
| R5 | Low | Frontend dev dependencies (vitest 3.x line, `tinypool`, `braces`) | Only a developer machine running the Vitest UI server is exposed | Not shipped; the UI server is not used; `pnpm audit --prod` is clean | Upgrade to vitest 4 | `pnpm audit` (all dependencies) after upgrade |

## What the authorization matrix does and does not show
The matrix (10 personas, 15 operations on the real stack) shows no unauthenticated access to protected operations, no customer access to staff or internal data, and correct separation between support, planner, scoped manager, buyer, category manager and administrator for the sampled operations. It samples one operation per area. Complete coverage comes from the route sweep (`tests/security/test_route_sweep.py`, every AI operation) and `SecurityPolicyTest` (Java path rules). Object-level rules (customer-to-customer, store and region scope) are proven by `api-e2e.sh` and `test_planning_db.py`, not by the matrix. In the matrix, AI `/metrics` shows 200 for everyone because the stack runs with `AI_ENV=local`; the unit tests prove it is protected otherwise (this is R10, not a bug).

## Unsafe external research: status
Controlled by the SafeFetcher; no open finding. Remaining exposure is R11 and the fact that exactly one live source is connected. Keep the allow-list short, keep `SOURCING_PROVIDERS` and `SOURCING_ALLOWED_HOSTS` out of user control, and never add a provider that takes a user-supplied URL.

## Dependency scanning and CI (recommendation only; nothing added)
The repository has no CI pipeline (`.github/` does not exist) although GitHub Actions is the declared DevOps target in `AGENTS.md`. A minimal pipeline needs no new platform:

| Job | Tool | Gate |
|---|---|---|
| Java | `mvn -B verify` plus OWASP dependency-check (needs an NVD API key stored as a CI secret) | fail on CVSS 7.0 or higher unless suppressed with a dated, owned reason |
| Python | `uv sync --frozen`, `pytest`, `pip-audit` on the exported lock file | fail on any known vulnerability with a fix available |
| Frontend | `pnpm install --frozen-lockfile`, `tsc -b`, `pnpm lint`, `vitest run`, `pnpm audit --prod` | fail on high or critical in production dependencies |
| Secrets | a secret scanner such as gitleaks over the diff | fail on a finding; `.env` stays ignored |
| Updates | Dependabot or Renovate for the three ecosystems | weekly pull requests; never auto-merge |
| Integration | Testcontainers jobs on a Docker-enabled runner; the throwaway-database Python integration suite | required for merge |

Run the scanners once manually first to size the backlog (R6 is "unknown", not "clean"). The real-stack scripts (`validate-all.sh`) and the model-dependent steps should stay manual or nightly because they need credentials and take about an hour.
